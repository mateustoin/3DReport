# Decisão 53: PATCH para correção ou doc, MINOR para funcionalidade nova (revisa a 27)

- **Data:** 2026-09-18
- **Status:** Aprovada

Revisão da decisão 27 (pedido do responsável do projeto): bump de **MINOR a cada leva** nunca deixava espaço pra `PATCH`, mesmo quando a leva era só uma correção pequena ou uma atualização de documentação — de `0.1.0` até `1.8.0`, todo bump real foi MINOR (`1.0.0` foi exceção forçada pelo bundler do macOS, decisão 34), nunca PATCH, apesar do próprio `development.md` já descrever PATCH como "correções isoladas fora de uma leva". Regra reforçada, alinhada a convenção usada em projetos profissionais (compatível com [Conventional Commits](https://www.conventionalcommits.org/pt-br/)): **PATCH** (`z`) para correção de bug isolada ou leva que só atualiza documentação, sem funcionalidade nova nem mudança de comportamento visível; **MINOR** (`y`) para leva que entrega funcionalidade nova ou melhoria visível ao usuário (mesmo critério de antes); **MAJOR** (`x`) continua reservado pra quebra de compatibilidade, sem caso de uso previsto. Critério de desempate: se uma leva mistura correção(ões) com funcionalidade nova, o bump segue sendo MINOR (a funcionalidade nova já exige isso) — PATCH é só pra levas que **não** têm nada de funcionalidade nova. Não muda onde a versão mora (`gradle.properties`/`AppVersion.kt`) nem o processo de "sempre bumpar, mesmo leva pequena" (decisão 31)
